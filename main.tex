\begin{cnabstract}
    许多算法原型止步于两个断点：脚本表达足够灵活，却难以触达 GPU；底层 CUDA 足够强大，却把使用者推向繁琐的内存管理和调度细节。本文围绕这一矛盾设计并实现 FTCL，一个 Tcl 风格的算法实验脚本系统，并将其扩展为面向计算几何的 CPU/CUDA 混合执行平台。FTCL 以 C++20 实现，支持变量、过程、作用域、列表、字典、数组、表达式、命令替换、源码加载、测试命令和线程通道。它的目标不是复刻完整 Tcl，而是提供一个足够小、足够清晰、又足以承载真实算法实验的控制层，让复杂计算可以被脚本组织、复现和扩展。

    系统核心是跨设备向量抽象 UVec。UVec 将一个逻辑向量映射为 CPU 缓冲区和多个 CUDA 缓冲区，通过有效标记维护最新副本，并在 CPU 或 CUDA 请求数据时自动完成同步。它还提供统一原始指针接口，使 CPU 算法和 CUDA kernel 能在同一命令模型下工作。基于 UVec，本文实现 geom 命令库，覆盖二维几何基础操作以及距离矩阵、最近点、圆形范围计数、包围盒归约、仿射变换和 AABB 碰撞检测等批量算法。实现中进一步将 UVec 句柄管理从全局锁细化为按句柄加锁，降低异构并发中的不必要串行化。

    本文从正确性、性能和应用三个层面评估 FTCL。语义回归、CPU/GPU 等价、随机差分和边界测试验证系统可靠性；单 GPU 与八卡 A800 多 GPU 实验显示，紧凑输出的范围计数可接近线性弱扩展，而距离矩阵受输出分配和内存带宽限制；并发实验揭示解释器调度、锁粒度和 GPU 资源竞争对吞吐量与尾延迟的影响。最后，本文将点、圆、包围盒和距离矩阵映射到海洋牧场感知、智慧港口安全、无人机水面巡检和船舶碰撞检测等场景。实验表明，FTCL 不只是几何函数集合，而是一个把脚本表达、跨设备内存、并发执行和可复现实验连接起来的异构空间计算原型。

\cnkeywords{脚本解释器；Tcl；计算几何；UVec；CUDA；多 GPU；海洋空间计算}
\end{cnabstract}

\begin{enabstract}
    Algorithm prototypes often break at the boundary between expression and execution: scripts are easy to write but rarely reach the GPU, while CUDA is powerful but forces users to manage memory, pointers, and synchronization by hand. This thesis addresses that gap by designing FTCL, a Tcl-style scripting system for algorithm experiments, and extending it into a CPU/CUDA hybrid computational geometry platform. Implemented in C++20, FTCL supports variables, procedures, scopes, lists, dictionaries, arrays, expressions, command substitution, source loading, testing commands, and thread channels. Its purpose is not to reproduce the whole Tcl language, but to provide a compact control layer that can organize, reproduce, and extend real computational workloads.

    The central abstraction is UVec, a cross-device vector that represents one logical vector through CPU and CUDA buffers. UVec tracks which copy is valid, synchronizes data on demand when a device requests the latest value, and exposes unified raw pointer interfaces for CPU algorithms and CUDA kernels. On top of UVec, the thesis implements a script-facing \texttt{geom} command library, including basic two-dimensional geometry operations and batch algorithms such as distance matrices, nearest point queries, circle range counting, bounding-box reduction, affine transformations, and AABB collision checks. The runtime also refines UVec handle management from one global lock to per-handle locking, reducing unnecessary serialization in heterogeneous concurrent workloads.

    The system is evaluated from correctness, performance, and application perspectives. Semantic regression tests, CPU/GPU equivalence tests, random differential tests, and edge-case tests validate reliability. Single-GPU and eight-GPU A800 experiments show that compact-output workloads such as circle range counting can achieve near-linear weak scaling, while output-heavy workloads such as distance matrices are limited by allocation and memory bandwidth. Concurrency experiments further reveal how interpreter scheduling, lock granularity, and GPU contention affect throughput and tail latency. Finally, the thesis maps points, circles, bounding boxes, and distance matrices to ocean-oriented scenarios such as marine ranch sensing, smart port safety, UAV water-surface inspection, and ship collision checking. The result is not merely a geometry library, but a prototype heterogeneous spatial-computing system that connects scripting, cross-device memory, concurrent execution, and reproducible evaluation.

\enkeywords{Scripting interpreter; Tcl; Computational geometry; UVec; CUDA; Multi-GPU; Marine spatial computing}
\end{enabstract}

\JOUBackmatterChapter{Conclusion and Future Work}
This thesis completed an end-to-end system that starts from a Tcl-style interpreter and grows into a CPU/CUDA hybrid computational geometry scripting platform. FTCL now supports a practical language subset, thread channels, UVec cross-device vectors, CPU geometry algorithms, CUDA kernels, tests, benchmarks, and thesis-ready figures. The experiments show that the GPU backend is most useful when work items are numerous and independent, while small inputs and immediate readback may erase the benefit of parallel execution.

Future work should proceed in four directions. First, UVec should be further aligned with the standard vector interface, including iterators, capacity management, insertion, erasure, and stronger exception-safety guarantees. Second, the CUDA backend should add memory pools, asynchronous streams, and better batching to reduce allocation and synchronization costs. Third, the parser path should continue moving toward token-stream parsing, AST representation, bytecode execution, and expression-level Pratt parsing. Fourth, the geometry library can be extended with spatial indexes, dynamic nearest-neighbor search, polygon boolean operations, and more realistic application demos.
