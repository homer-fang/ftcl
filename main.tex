\begin{cnabstract}
    本文设计并实现了 FTCL——一种面向算法实验的 Tcl 风格脚本解释器，并将其扩展为 CPU/CUDA 混合计算几何系统。工作从 C++20 实现的轻量级解释器核心出发，核心支持变量、命令求值、过程、作用域、列表与字典、数组、表达式求值、命令替换、源码加载、测试命令以及回归测试框架。在语言运行时之上，项目引入线程任务与线程通道，使脚本能够描述并发的生产者—消费者工作负载。

    本文的主要扩展是一个面向几何的异构计算层。设计名为 UVec 的跨设备向量抽象，在统一逻辑向量接口下管理 CPU 与 CUDA 缓冲区。UVec 记录当前有效副本，并在设备请求最新数据时自动在 CPU 与 CUDA 之间同步，同时为两类后端提供统一的原始指针接口。实现还将 UVec 句柄管理从粗粒度全局锁细化为按句柄条目加锁，使独立几何任务可在不同设备上并发执行。基于 UVec，本文实现了 geom 命令库，涵盖基础二维几何运算以及距离矩阵、最近点查询、圆形范围计数、包围盒归约、仿射变换与 AABB 碰撞检测等批量算法。

    本文通过语义回归测试、CPU/GPU 等价性测试、随机差分测试、边界用例测试、CPU/CUDA 性能扩展实验、多 GPU 扩展实验以及并发几何负载对系统进行评估。在八卡 A800 服务器上，多 GPU 弱扩展实验表明，圆形范围计数等紧凑输出算法可接近线性扩展，而距离矩阵等大规模输出算法则暴露输出分配与内存带宽瓶颈。应用章节还将几何系统与海洋导向的空间计算场景相联系，包括海洋牧场感知、智慧港口安全、无人机水面巡检与船舶碰撞检测。项目表明，紧凑脚本语言可作为海洋空间分析、计算几何与异构执行的实际控制层。

    FTCL 并非单纯的几何函数集合，而是连接脚本语言、运行时数据结构、并发原语、跨设备内存管理、CPU 算法、CUDA 内核、多 GPU 实验与可复现基准产物的完整实验平台。因此，本文聚焦系统集成：小型解释器如何控制大规模算法负载、类向量数据如何在脚本层隐藏底层内存操作的情况下在 CPU 与 GPU 间流转、锁粒度如何影响异构并发，以及如何用测试与生成图表支撑性能结论。

    最终系统提供四层贡献：第一，解释器层提供易于实现且足以表达算法脚本的 Tcl 风格命令模型；第二，UVec 层抽象 CPU/CUDA 同步，建立面向外部函数风格后端调用的统一指针桥梁，并以更细粒度句柄锁避免不必要串行化；第三，几何层通过竞赛常见算法、碰撞检测、空间查询与海洋监测任务展示运行时实用价值；第四，评估层包含 CPU 基线、CPU/GPU 等价性检验、单 GPU 加速比、多 GPU 弱扩展测量与论文级图表。本文还讨论解析开销、CUDA 盈亏平衡点、读回成本，以及未来引入内存池与基于流的调度等局限。

\cnkeywords{脚本解释器；Tcl；计算几何；CUDA；多 GPU；海洋空间计算}
\end{cnabstract}

\begin{enabstract}
    This thesis designs and implements FTCL, a Tcl-style scripting interpreter for algorithm experiments, and extends it into a CPU/CUDA hybrid computational geometry system. The work starts from a lightweight interpreter core implemented in C++20. The core supports variables, command evaluation, procedures, scopes, list and dictionary values, arrays, expression evaluation, command substitution, source loading, testing commands, and a regression test harness. On top of the language runtime, the project introduces thread tasks and thread channels, allowing scripts to describe concurrent producer-consumer workloads.

    The main extension of this thesis is a geometry-oriented heterogeneous computing layer. A cross-device vector abstraction named UVec is designed to manage CPU and CUDA buffers under one logical vector interface. UVec records which copy is currently valid, automatically copies data from CPU to CUDA or from CUDA to CPU when a device requests the latest value, and exposes unified raw pointer interfaces for CPU and CUDA backends. The implementation also refines UVec handle management from a coarse global lock to per-handle entry locks, so independent geometry workloads can run concurrently on different devices. Based on UVec, the thesis implements a geom command library. The library covers basic two-dimensional geometry operations and batch algorithms such as distance matrices, nearest point queries, circle range counting, bounding-box reduction, affine transformations, and AABB collision checks.
    
    The thesis evaluates the system using semantic regression tests, CPU/GPU equivalence tests, random differential tests, edge-case tests, CPU/CUDA performance scaling experiments, multi-GPU scaling experiments, and concurrent geometry workloads. On an eight-GPU A800 server, the multi-GPU weak-scaling experiment shows that compact-output algorithms such as circle range counting can scale close to linearly, while large-output algorithms such as distance matrices expose output-allocation and memory-traffic bottlenecks. Finally, the application chapter connects the geometry system to ocean-oriented spatial computing scenarios, including marine ranch sensing, smart port safety, UAV water-surface inspection, and ship collision checking. The project demonstrates that a compact scripting language can serve as a practical control layer for marine spatial analysis, computational geometry, and heterogeneous execution.
    
    
    FTCL is not only a collection of geometry functions. It is a complete experimental platform that connects a scripting language, runtime data structures, concurrency primitives, cross-device memory management, CPU algorithms, CUDA kernels, multi-GPU experiments, and reproducible benchmark artifacts. This thesis therefore focuses on system integration: how a small interpreter can control large-scale algorithmic workloads, how vector-like data can move between CPU and GPU without exposing low-level memory operations to scripts, how lock granularity affects heterogeneous concurrency, and how performance claims can be supported by tests and generated figures.
    
    The final system provides four layers of contribution. First, the interpreter layer offers a Tcl-like command model that is simple enough to implement yet expressive enough for algorithm scripts. Second, the UVec layer abstracts CPU/CUDA synchronization, creates a unified pointer bridge for foreign-function style backend calls, and uses finer-grained handle locking to avoid unnecessary serialization. Third, the geometry layer demonstrates the practical value of this runtime through algorithms that are common in programming contests, collision detection, spatial queries, and ocean-oriented monitoring tasks. Fourth, the evaluation layer includes CPU baselines, CPU/GPU equivalence checks, single-GPU speedups, multi-GPU weak-scaling measurements, and thesis-ready figures. The thesis also discusses limitations, including parser overhead, CUDA break-even behavior, readback cost, and the need for future memory-pool and stream-based scheduling.
    
\enkeywords{Scripting interpreter; Tcl; Computational geometry; CUDA; Multi-GPU; Marine spatial computing}
\end{enabstract}

\JOUBackmatterChapter{Conclusion and Future Work}
This thesis completed an end-to-end system that starts from a Tcl-style interpreter and grows into a CPU/CUDA hybrid computational geometry scripting platform. FTCL now supports a practical language subset, thread channels, UVec cross-device vectors, CPU geometry algorithms, CUDA kernels, tests, benchmarks, and thesis-ready figures. The experiments show that the GPU backend is most useful when work items are numerous and independent, while small inputs and immediate readback may erase the benefit of parallel execution.

Future work should proceed in four directions. First, UVec should be further aligned with the standard vector interface, including iterators, capacity management, insertion, erasure, and stronger exception-safety guarantees. Second, the CUDA backend should add memory pools, asynchronous streams, and better batching to reduce allocation and synchronization costs. Third, the parser path should continue moving toward token-stream parsing, AST representation, bytecode execution, and expression-level Pratt parsing. Fourth, the geometry library can be extended with spatial indexes, dynamic nearest-neighbor search, polygon boolean operations, and more realistic application demos.
