\chapter{System Design}

\section{Overview}
The architecture of FTCL is shown in Figure \ref{fig:system-arch}. A script is parsed into commands and words. The interpreter evaluates words, performs substitutions, and dispatches commands. The \texttt{geom} command parses geometry arguments or UVec handles and then selects either the CPU backend or the CUDA backend. UVec sits between the interpreter and the backends, managing cross-device data movement.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.96\textwidth]{system-architecture.png}
  \caption{Overall architecture of the FTCL geometry scripting system}
  \label{fig:system-arch}
\end{figure}

The architecture separates concerns clearly. The parser and interpreter handle language semantics. The command layer exposes stable user-facing operations. UVec manages data location and synchronization. The CPU and CUDA backends implement algorithms.

\section{Interpreter Runtime}
The runtime contains values, words, scripts, scopes, and commands. A Value stores the script-level value. A Word represents one command argument before or after substitution. A Script is a list of commands. The interpreter maintains command tables and variable scopes.

The normal execution path is:

\begin{enumerate}
  \item Parse the source text into a script structure.
  \item Evaluate one command at a time.
  \item Evaluate each word by applying variable substitution, command substitution, array lookup, and string concatenation as needed.
  \item Use the first evaluated word as the command name.
  \item Call the native C++ command function and return either a value or an exception.
\end{enumerate}

This structure is intentionally close to Tcl. It makes the language small but extensible. New capabilities such as \texttt{thread}, \texttt{uvec}, and \texttt{geom} are integrated as commands rather than as new syntax.

\section{Lexical Analysis Flow}
The lexical layer converts a raw script string into a stream of tokens. FTCL's token-stream direction keeps token text and token boundaries so later stages can reason about command endings, comments, whitespace, braces, brackets, variable references, and ordinary text. The following pseudocode summarizes the intended lexer flow.

\begin{lstlisting}[caption={Pseudocode for FTCL lexical analysis}]
procedure TOKENIZE(source):
    tokens = []
    cursor = 0

    while cursor < length(source):
        ch = source[cursor]

        if ch is space or tab:
            start = cursor
            consume horizontal whitespace
            tokens.push(Token(Whitespace, source[start:cursor]))

        else if ch is newline or ch is ';':
            tokens.push(Token(CommandEnd, ch))
            cursor = cursor + 1

        else if ch is '#'
             and current position is at command start:
            start = cursor
            consume until newline or end of file
            tokens.push(Token(Comment, source[start:cursor]))

        else if ch is one of '{', '}', '[', ']', '$', '"', '\\':
            tokens.push(Token(Special, ch))
            cursor = cursor + 1

        else:
            start = cursor
            consume ordinary characters until a special boundary
            tokens.push(Token(Text, source[start:cursor]))

    tokens.push(Token(EndOfFile, ""))
    return tokens
\end{lstlisting}

The lexer does not execute substitutions. It only records the observable structure of the input. This separation is useful because Tcl-style substitution is semantic: a dollar sign may later require variable lookup, and a bracketed script may later require recursive command evaluation.

\section{Syntax Analysis Flow}
The parser consumes tokens and groups them into commands and words. A command ends at a newline, semicolon, or end-of-file, except when the parser is inside braces, quotes, or brackets. The parser does not execute commands. It only builds a script representation that can be evaluated later.

\begin{lstlisting}[caption={Pseudocode for token-stream command parsing}]
procedure PARSE_SCRIPT(tokens):
    cursor = TokenCursor(tokens)
    script = []

    while not cursor.at_end():
        cursor.skip_whitespace_and_comments()

        if cursor.at_command_end():
            cursor.next()
            continue

        command = PARSE_COMMAND(cursor)
        script.commands.push(command)

        if cursor.at_command_end():
            cursor.next()
        else if not cursor.at_end():
            error("expected command boundary")

    return script

procedure PARSE_COMMAND(cursor):
    words = []

    while not cursor.at_end() and not cursor.at_command_end():
        cursor.skip_inline_whitespace()

        if cursor.at_command_end() or cursor.at_end():
            break

        word = PARSE_WORD(cursor)
        words.push(word)

    return Command(words)
\end{lstlisting}

The word parser is more detailed than the command parser because a word may contain literal text, variable references, command substitutions, array references, braced literals, quoted strings, and expansion syntax. The important design decision is that the parser stores these pieces as structured word nodes, while the interpreter decides their runtime values.

\begin{lstlisting}[caption={Pseudocode for word parsing}]
procedure PARSE_WORD(cursor):
    if cursor.match("{"):
        return Word.Value(read_balanced_braced_text(cursor))

    if cursor.match("\""):
        parts = []
        while not cursor.match("\""):
            parts.push(PARSE_WORD_PART(cursor, quoted = true))
        return Word.Tokens(parts)

    if cursor.match("{*}"):
        child = PARSE_WORD(cursor)
        return Word.Expand(child)

    parts = []
    while not cursor.at_word_boundary():
        parts.push(PARSE_WORD_PART(cursor, quoted = false))

    if parts has one literal part:
        return Word.Value(parts[0])
    return Word.Tokens(parts)

procedure PARSE_WORD_PART(cursor, quoted):
    if cursor.peek() == '$':
        return PARSE_VARIABLE_REFERENCE(cursor)
    if cursor.peek() == '[':
        return Word.Script(read_balanced_bracket_script(cursor))
    if cursor.peek() == '\\':
        return Word.String(parse_backslash_sequence(cursor))
    return Word.String(read_literal_text(cursor, quoted))
\end{lstlisting}

\section{Semantic Execution Flow}
Semantic execution begins after parsing. The interpreter evaluates each command in order. Each word is resolved into a runtime value. The first value becomes the command name, and the remaining values become arguments. The command function then performs the actual operation.

\begin{lstlisting}[caption={Pseudocode for FTCL semantic execution}]
procedure EVAL_SCRIPT(interp, script):
    result = empty string

    for command in script.commands:
        if command.words is empty:
            continue

        values = []
        for word in command.words:
            value_or_values = EVAL_WORD(interp, word)

            if word is Expand:
                values.extend(parse_list(value_or_values))
            else:
                values.push(value_or_values)

        command_name = values[0].as_string()
        arguments = values

        command_proc = interp.lookup_command(command_name)
        if command_proc is missing:
            error("invalid command name")

        result = command_proc(interp, arguments)

        if result.code is RETURN, BREAK, CONTINUE, or ERROR:
            propagate result according to the current context

    return result

procedure EVAL_WORD(interp, word):
    match word.kind:
        Value:
            return word.literal
        String:
            return word.text
        VarRef:
            return interp.lookup_variable(word.name)
        ArrayRef:
            index = EVAL_WORD(interp, word.index)
            return interp.lookup_array_element(word.name, index)
        Script:
            return EVAL_SCRIPT(interp, PARSE_SCRIPT(TOKENIZE(word.script)))
        Tokens:
            output = ""
            for part in word.parts:
                output = output + EVAL_WORD(interp, part).as_string()
            return output
\end{lstlisting}

\section{UVec Cross-device Design}
UVec is designed as a vector-like container that can own both CPU and CUDA storage. A normal \texttt{std::vector<T>} owns only CPU memory. UVec owns a CPU buffer and optional CUDA buffers. It also records which device currently has a valid and up-to-date copy.

When CPU code asks for the latest data but the newest copy is on CUDA, UVec performs a CUDA-to-CPU copy. When a CUDA kernel asks for the latest data but the newest copy is on CPU, UVec performs a CPU-to-CUDA copy. When a mutable pointer is requested on one device, other copies are marked invalid because the target device may write new data.

The two most important pointer interfaces are \texttt{as\_uptr(device)} and \texttt{as\_mut\_uptr(device)}. The first returns a read-only pointer after making the target device valid. The second returns a mutable pointer and marks the target device as the newest writer.

\section{Formal UVec Consistency Model}
UVec can be described as a small consistency model over a set of devices. Let
\[
  D = \{\mathrm{CPU}, \mathrm{CUDA}_0, \mathrm{CUDA}_1, \ldots\}
\]
be the set of possible storage devices. A UVec instance of length \(n\) is represented as
\[
  U = (n, B, V, L),
\]
where \(B_d\) is the physical buffer on device \(d \in D\), \(V_d \in \{0,1\}\) indicates whether \(B_d\) contains a valid copy of the logical vector, and \(L \subseteq D\) is the set of devices that may contain the latest value. In the current implementation, the common case behaves like a single latest writer, but the set notation allows a state where CPU and CUDA are both valid after a read synchronization.

The two core operations obey the following rules.

\begin{description}
  \item[Read rule:] \texttt{as\_uptr(d)} must return a pointer on device \(d\) only after ensuring \(V_d = 1\). If \(V_d = 0\), the operation copies from any device \(s\) such that \(V_s = 1\) and then sets \(V_d \leftarrow 1\). This operation does not invalidate other valid copies.
  \item[Write rule:] \texttt{as\_mut\_uptr(d)} must return a mutable pointer on device \(d\). Before returning, it ensures that \(B_d\) exists and contains the latest value. It then sets \(V_d \leftarrow 1\) and \(V_s \leftarrow 0\) for all \(s \ne d\), because a later write through the returned pointer may change the logical vector.
\end{description}

These rules imply two useful invariants:
\[
  \exists d \in D,\; V_d = 1
\]
after every successfully initialized UVec operation, and every read pointer returned by UVec refers to a valid copy of the logical vector at the time of return. This model is deliberately simple. It is strong enough for synchronous CPU/CUDA command execution, while still leaving room for future extensions such as multiple CUDA devices, asynchronous streams, or copy-on-write policies.

\section{Geometry Command Flow}
The command execution flow is shown in Figure \ref{fig:geom-flow}. For a command such as \texttt{geom nearest\_point}, the interpreter first evaluates the script arguments. The command then parses UVec handles and device options. If the target device is CPU, the input data is synchronized to CPU and the C++ algorithm is called. If the target device is CUDA, the input data is synchronized to CUDA, an output UVec is created, a CUDA kernel is launched, and the output handle is returned.

\begin{figure}[H]
  \centering

Using handles is important. Large point sets should not be repeatedly converted into script strings. Instead, a script can create a UVec once, pass its handle to multiple commands, and read back the result only when necessary.

\section{Concurrency Design}
FTCL provides thread tasks and thread channels. A thread task runs a script asynchronously and can be awaited later. A thread channel stores messages in a queue protected by a mutex and a condition variable. It supports blocking receive and non-blocking try-receive.

This concurrency model is useful for experiments. It can drive a game-like demo, simulate producer-consumer workloads, and dispatch multiple geometry requests through worker scripts. The current CUDA concurrency experiment also reveals a limitation: multiple script workers can contend for one GPU, so future work should add streams or a dedicated GPU scheduler.
