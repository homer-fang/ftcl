\section{总体架构}
FTCL 的总体架构如图 \ref{fig:system-arch} 所示。一个脚本首先被解析为命令（commands）和词（words），随后由解释器（interpreter）对词进行求值，完成变量替换、命令替换、数组访问和字符串拼接，最后将第一个求值结果作为命令名进行分发。\texttt{geom} 命令位于语言层和计算层之间：它负责解析几何参数或 UVec 句柄，并根据用户指定的设备（device）选择 CPU 后端或 CUDA 后端。UVec 则处在命令层与后端层之间，负责维护跨设备数据的位置、有效性和同步过程。

\begin{figure}[H]
  \centering
  \includegraphics[width=0.96\textwidth]{system-architecture.png}
  \caption{FTCL 几何脚本系统总体架构（FTCL geometry scripting system architecture）}
  \label{fig:system-arch}
\end{figure}

这一设计的核心是分层而不是堆叠。解析器与解释器专注于语言语义；命令层提供稳定的用户接口；UVec 负责数据驻留（data residency）与同步；CPU/CUDA 后端只实现具体算法。这样做的好处是：语言可以继续扩展，几何算法可以继续增加，CUDA 路径也可以在不破坏脚本接口的情况下逐步优化。

\section{解释器运行时（Interpreter Runtime）}
\textbf{运行时}（runtime）由值（values）、词（words）、脚本（scripts）、作用域（scopes）和命令（commands）组成。\texttt{Value} 表示脚本层的值；\texttt{Word} 表示一个命令参数在求值前后的结构；\texttt{Script} 是命令列表；解释器维护命令表与变量作用域。FTCL 的执行路径保持 Tcl 风格的简单性，但在内部为后续扩展保留了结构化表示。

一个普通脚本的执行过程如下：

\begin{enumerate}
  \item 将 source text 解析为 script structure。
  \item 按顺序执行一个个 command。
  \item 对每个 word 执行 variable substitution、command substitution、array lookup 和 string concatenation。
  \item 将第一个求值后的 word 作为 command name。
  \item 调用对应的 native C++ command function，并返回 value 或 exception。
\end{enumerate}

这种结构有一个重要优势：新能力不需要发明新语法。\texttt{thread}、\texttt{uvec} 和 \texttt{geom} 都是 command，而不是语言核心的特殊分支。因此 FTCL 可以保持小而清晰，同时承载并发、跨设备内存和几何算法。

\section{词法分析流程（Lexical Analysis Flow）}
\textbf{词法层}（lexical layer）将原始脚本字符串转换为 token 流（token stream）。FTCL 的词法流方向会保留 token 文本与 token 边界，使后续阶段能明确识别命令结束符、注释、空白、花括号、方括号、变量引用和普通文本。算法 \ref{alg:lexer} 描述了词法分析器（lexer）的基本流程。

\begin{algorithm}[H]
\caption{FTCL Lexical Analysis}
\label{alg:lexer}
\KwInput{source string $source$}
\KwOutput{token stream $tokens$}
$tokens \leftarrow [\ ]$\;
$cursor \leftarrow 0$\;
\While{$cursor < |source|$}{
  $ch \leftarrow source[cursor]$\;
  \uIf{$ch \in \{\mathrm{space},\mathrm{tab}\}$}{
    $start \leftarrow cursor$\;
    consume horizontal whitespace\;
    append \textsc{Token}(\textsc{Whitespace}, $source[start:cursor]$) to $tokens$\;
  }
  \uElseIf{$ch$ is a newline or $ch = \texttt{;}$}{
    append \textsc{Token}(\textsc{CommandEnd}, $ch$) to $tokens$\;
    $cursor \leftarrow cursor + 1$\;
  }
  \uElseIf{$ch = \texttt{\#}$ and $cursor$ is at command start}{
    $start \leftarrow cursor$\;
    consume until newline or end of file\;
    append \textsc{Token}(\textsc{Comment}, $source[start:cursor]$) to $tokens$\;
  }
  \uElseIf{$ch$ is a Tcl special delimiter}{
    append \textsc{Token}(\textsc{Special}, $ch$) to $tokens$\;
    $cursor \leftarrow cursor + 1$\;
  }
  \Else{
    $start \leftarrow cursor$\;
    consume ordinary characters until a token boundary\;
    append \textsc{Token}(\textsc{Text}, $source[start:cursor]$) to $tokens$\;
  }
}
append \textsc{Token}(\textsc{EndOfFile}, empty string) to $tokens$\;
\KwReturn{$tokens$}\;
\end{algorithm}

Lexer 不执行 substitution。它只记录输入中可观察的结构。这样做非常重要，因为 Tcl-style substitution 本质上是 semantic action：\texttt{\$} 可能需要 variable lookup，\texttt{[...]} 可能需要 recursive command evaluation。把 tokenization 和 evaluation 分开，可以让 parser 更稳定，也便于错误定位和回归测试。

\section{语法分析流程（Syntax Analysis Flow）}
\textbf{解析器}（parser）消费 token 流，并将 token 分组为命令与词。命令在换行、分号或文件结束处终止；若解析器位于花括号、引号或方括号内部，则这些符号不再表示命令边界。解析器不执行命令，只构造后续可执行的脚本表示。

\begin{algorithm}[H]
\caption{Token-stream Command Parsing}
\label{alg:parse-script}
\KwInput{token stream $tokens$}
\KwOutput{script object $script$}
\Proc{\textsc{ParseScript}($tokens$)}{
  $cursor \leftarrow \textsc{TokenCursor}(tokens)$\;
  $script \leftarrow [\ ]$\;
  \While{not $cursor.atEnd()$}{
    $cursor.skipWhitespaceAndComments()$\;
    \If{$cursor.atCommandEnd()$}{
      $cursor.next()$\;
      \textbf{continue}\;
    }
    $command \leftarrow \textsc{ParseCommand}(cursor)$\;
    append $command$ to $script.commands$\;
    \uIf{$cursor.atCommandEnd()$}{
      $cursor.next()$\;
    }
    \uElseIf{not $cursor.atEnd()$}{
      raise ``expected command boundary''\;
    }
  }
  \KwReturn{$script$}\;
}
\Proc{\textsc{ParseCommand}($cursor$)}{
  $words \leftarrow [\ ]$\;
  \While{not $cursor.atEnd()$ and not $cursor.atCommandEnd()$}{
    $cursor.skipInlineWhitespace()$\;
    \If{$cursor.atCommandEnd()$ or $cursor.atEnd()$}{
      \textbf{break}\;
    }
    $word \leftarrow \textsc{ParseWord}(cursor)$\;
    append $word$ to $words$\;
  }
  \KwReturn{\textsc{Command}($words$)}\;
}
\end{algorithm}

\textbf{词法解析器}（word parser）比命令解析器更细，因为一个 word 内部可能包含字面文本、变量引用、命令替换、数组引用、花括号字面量、引号字符串与展开语法。关键设计是：解析器将这些组成部分保存为结构化 word 节点，而解释器负责决定它们在运行时的值。

\begin{algorithm}[H]
\caption{Word Parsing}
\label{alg:parse-word}
\KwInput{token cursor $cursor$}
\KwOutput{word node}
\Proc{\textsc{ParseWord}($cursor$)}{
  \uIf{$cursor$ matches an open brace}{
    \KwReturn{\textsc{Word.Value}(\textsc{ReadBalancedBracedText}($cursor$))}\;
  }
  \uElseIf{$cursor$ matches a quote}{
    $parts \leftarrow [\ ]$\;
    \While{$cursor$ does not match the closing quote}{
      append \textsc{ParseWordPart}($cursor$, true) to $parts$\;
    }
    \KwReturn{\textsc{Word.Tokens}($parts$)}\;
  }
  \uElseIf{$cursor$ matches the expansion prefix \texttt{\{*\}}}{
    $child \leftarrow \textsc{ParseWord}(cursor)$\;
    \KwReturn{\textsc{Word.Expand}($child$)}\;
  }
  $parts \leftarrow [\ ]$\;
  \While{not $cursor.atWordBoundary()$}{
    append \textsc{ParseWordPart}($cursor$, false) to $parts$\;
  }
  \uIf{$parts$ contains one literal part}{
    \KwReturn{\textsc{Word.Value}($parts[0]$)}\;
  }
  \Else{
    \KwReturn{\textsc{Word.Tokens}($parts$)}\;
  }
}
\Proc{\textsc{ParseWordPart}($cursor$, $quoted$)}{
  \uIf{$cursor.peek() = \texttt{\$}$}{
    \KwReturn{\textsc{ParseVariableReference}($cursor$)}\;
  }
  \uElseIf{$cursor.peek() = \texttt{[}$}{
    \KwReturn{\textsc{Word.Script}(\textsc{ReadBalancedBracketScript}($cursor$))}\;
  }
  \uElseIf{$cursor.peek()$ is a backslash}{
    \KwReturn{\textsc{Word.String}(\textsc{ParseBackslashSequence}($cursor$))}\;
  }
  \Else{
    \KwReturn{\textsc{Word.String}(\textsc{ReadLiteralText}($cursor$, $quoted$))}\;
  }
}
\end{algorithm}

\section{语义执行流程（Semantic Execution Flow）}
\textbf{语义执行}（semantic execution）发生在语法分析之后。解释器逐条执行命令，对每个词求值，并把第一个值作为命令名，其余值作为参数。命令函数才真正改变变量、创建 UVec、启动 CUDA kernel 或返回结果。

\begin{algorithm}[H]
\caption{Command-level Semantic Execution}
\label{alg:semantic-exec}
\KwInput{interpreter $interp$, parsed script $script$}
\KwOutput{last command result}
\Proc{\textsc{EvalScript}($interp$, $script$)}{
  $result \leftarrow$ empty string\;
  \ForEach{$command \in script.commands$}{
    \If{$command.words$ is empty}{
      \textbf{continue}\;
    }
    $values \leftarrow [\ ]$\;
    \ForEach{$word \in command.words$}{
      $value \leftarrow \textsc{EvalWord}(interp, word)$\;
      \uIf{$word$ is an expansion word}{
        extend $values$ by \textsc{ParseList}($value$)\;
      }
      \Else{
        append $value$ to $values$\;
      }
    }
    $name \leftarrow values[0].asString()$\;
    $proc \leftarrow interp.lookupCommand(name)$\;
    \If{$proc$ is missing}{
      raise ``invalid command name''\;
    }
    $result \leftarrow proc(interp, values)$\;
    \If{$result.code$ is \textsc{Return}, \textsc{Break}, \textsc{Continue}, or \textsc{Error}}{
      propagate $result$ according to the current context\;
    }
  }
  \KwReturn{$result$}\;
}
\end{algorithm}

\begin{algorithm}[H]
\caption{Word Evaluation}
\label{alg:word-eval}
\KwInput{interpreter $interp$, word node $word$}
\KwOutput{runtime value}
\Proc{\textsc{EvalWord}($interp$, $word$)}{
  \uIf{$word.kind = \textsc{Value}$}{
    \KwReturn{$word.literal$}\;
  }
  \uElseIf{$word.kind = \textsc{String}$}{
    \KwReturn{$word.text$}\;
  }
  \uElseIf{$word.kind = \textsc{VarRef}$}{
    \KwReturn{$interp.lookupVariable(word.name)$}\;
  }
  \uElseIf{$word.kind = \textsc{ArrayRef}$}{
    $index \leftarrow \textsc{EvalWord}(interp, word.index)$\;
    \KwReturn{$interp.lookupArrayElement(word.name, index)$}\;
  }
  \uElseIf{$word.kind = \textsc{Script}$}{
    \KwReturn{\textsc{EvalScript}($interp$, \textsc{ParseScript}(\textsc{Tokenize}($word.script$)))}\;
  }
  \Else{
    $output \leftarrow$ empty string\;
    \ForEach{$part \in word.parts$}{
      $output \leftarrow output + \textsc{EvalWord}(interp, part).asString()$\;
    }
    \KwReturn{$output$}\;
  }
}
\end{algorithm}

\section{UVec 跨设备设计}
UVec 是一个\textbf{类向量容器}（vector-like container），但它不只拥有 CPU 存储。普通 \texttt{std::vector<T>} 只维护 CPU 内存；UVec 同时维护 CPU 缓冲区与可选 CUDA 缓冲区，并记录哪一个设备上的数据是有效且最新的。

当 CPU code 请求最新数据，而最新副本在 CUDA 上时，UVec 执行 CUDA-to-CPU copy；当 CUDA kernel 请求最新数据，而最新副本在 CPU 上时，UVec 执行 CPU-to-CUDA copy；当某个 device 请求 mutable pointer 时，其他副本会被标记为 invalid，因为该 device 可能写入新值。图 \ref{fig:uvec-sync} 展示同步机制，图 \ref{fig:uvec-state} 展示状态机视角。

\begin{figure}[H]

  \caption{UVec 跨设备同步机制（Cross-device synchronization in UVec）}

\end{figure}

最重要的两个 pointer interfaces 是 \texttt{as\_uptr(device)} 和 \texttt{as\_mut\_uptr(device)}。前者返回 read-only pointer，并保证目标 device 上的数据已经 valid；后者返回 mutable pointer，并将目标 device 标记为 newest writer。这两个接口让 CPU algorithm 和 CUDA kernel 可以共享同一个数据抽象，而不需要脚本用户手动判断数据在哪里。

\section{形式化 UVec 一致性模型}
UVec 可以被描述为定义在设备集合上的小型\textbf{一致性模型}（consistency model）。令
\[
  D = \{\mathrm{CPU}, \mathrm{CUDA}_0, \mathrm{CUDA}_1, \ldots\}
\]
表示可能的存储设备集合。长度为 \(n\) 的 UVec instance 表示为
\[
  U = (n, B, V, L),
\]
其中 \(B_d\) 是 device \(d \in D\) 上的 physical buffer，\(V_d \in \{0,1\}\) 表示 \(B_d\) 是否包含 valid copy，\(L \subseteq D\) 表示可能包含 latest value 的 device set。当前实现通常表现为 single latest writer，但集合表示允许 CPU 和 CUDA 在一次 read synchronization 后同时 valid。

两个核心操作满足以下规则：

\begin{description}
  \item[Read rule:] \texttt{as\_uptr(d)} 只有在保证 \(V_d = 1\) 后才能返回 device \(d\) 上的 pointer。如果 \(V_d = 0\)，则从某个满足 \(V_s = 1\) 的 source device \(s\) 复制数据，并设置 \(V_d \leftarrow 1\)。Read operation 不会使其他 valid copies 失效。
  \item[Write rule:] \texttt{as\_mut\_uptr(d)} 返回 device \(d\) 上的 mutable pointer。返回前必须保证 \(B_d\) 存在且包含 latest value；随后设置 \(V_d \leftarrow 1\)，并对所有 \(s \ne d\) 设置 \(V_s \leftarrow 0\)，因为通过 mutable pointer 的后续写入可能改变 logical vector。
\end{description}

在上述规则下，可进一步形式化证明 UVec 维持有效副本的不变式。若 UVec 在初始化完成后满足
\[
  \exists d \in D,\quad V_d = 1,
\]
且后续状态变化仅由 \(\mathrm{as\_uptr}(d)\) 与 \(\mathrm{as\_mut\_uptr}(d)\) 两类操作产生，则对任意有限操作序列，下列两个性质成立：
\begin{align}
  &\exists d \in D,\quad V_d = 1; \label{eq:uvec-invariant}\\
  &\mathrm{as\_uptr}(d)\ \text{成功返回时必有}\ V_d = 1. \label{eq:uvec-read-valid}
\end{align}

\begin{proof}
对操作序列长度 \(k\) 做数学归纳，先证明性质~\eqref{eq:uvec-invariant}，再说明性质~\eqref{eq:uvec-read-valid} 在每次读操作中同时成立。

\medskip\noindent\textbf{归纳奠基。}当 \(k = 0\) 时，系统尚未执行任何后续操作。根据 UVec 的初始化条件，至少存在一个设备 \(d \in D\) 满足 \(V_d = 1\)，命题显然成立；这也是代码执行后必然产生的结果。

\medskip\noindent\textbf{归纳假设。}当操作序列长度为 \(k\) 时命题成立，即执行前 \(k\) 次操作后，至少存在一个设备 \(s \in D\) 满足 \(V_s = 1\)。

\medskip\noindent\textbf{归纳递推。}考虑第 \(k+1\) 次操作，该操作有两种可能。

\smallskip\noindent\textit{第一种情况：}第 \(k+1\) 次操作为 \(\mathrm{as\_uptr}(d)\)。

若操作前有 \(V_d = 1\)，则设备 \(d\) 上已有有效Copy，操作可直接返回只读指针，不变式~\eqref{eq:uvec-invariant} 显然成立，且读指针有效性~\eqref{eq:uvec-read-valid} 也成立。

若操作前有 \(V_d = 0\)，根据归纳假设，存在某个设备 \(s \in D\) 满足 \(V_s = 1\)。根据 UVec 的读规则，系统会从有效源设备 \(s\) 将数据同步到目标设备 \(d\)，并设置 \(V_d \leftarrow 1\)。读操作不会使其他有效副本失效，因此操作后至少设备 \(d\) 是有效副本，从而仍有
\[
  \exists d \in D,\quad V_d = 1.
\]
同时，由于 \(\mathrm{as\_uptr}(d)\) 返回前已保证 \(V_d = 1\)，故返回的只读指针必然指向目标设备上的有效Copy。

\smallskip\noindent\textit{第二种情况：}第 \(k+1\) 次操作为 \(\mathrm{as\_mut\_uptr}(d)\)。

根据 UVec 的写规则，系统在返回可变指针前会保证 \(d\) 上存在当前逻辑向量的最新数据，随后将设备 \(d\) 标记为有效，并将其他设备上的旧Copy标记为无效，即
\[
  V_d \leftarrow 1,\qquad V_s \leftarrow 0 \quad (s \ne d).
\]
因此，即使其他设备Copy失效，设备 \(d\) 仍是有效Copy，操作后仍然满足
\[
  \exists d \in D,\quad V_d = 1.
\]
此情形下未调用读接口，故只需维护不变式~\eqref{eq:uvec-invariant}。

\medskip\noindent综上所述，第 \(k\) 次操作后不变式成立，第 \(k+1\) 次操作后不变式仍然成立。根据数学归纳法可知，对任意有限操作序列，UVec 始终至少保留一份有效Copy；并且每次 \(\mathrm{as\_uptr}(d)\) 成功返回时，目标设备 \(d\) 的 Copy 一定有效。
\end{proof}

Handle 机制非常关键。大规模点集不应该在每条命令之间反复转换为 script strings。更合理的方式是：script 创建一次 UVec，把 handle 传给多个 geometry commands，只在最终需要展示或统计时再 read back。这个思路也是后面 performance evaluation 中 speedup 能出现的前提。

\section{并发设计}
FTCL 提供线程任务（thread tasks）与线程通道（thread channels）。线程任务可以异步运行一段脚本并在之后被等待（await）；线程通道是由互斥锁与条件变量保护的消息队列，支持阻塞接收与非阻塞尝试接收。

这个 concurrency model 对实验很有用。它可以驱动 game-like demo，模拟 producer-consumer workload，也可以通过多个 worker scripts 分发 geometry requests。当前 CUDA concurrency experiment 也暴露出一个限制：多个 script workers 可能竞争同一个 GPU，所以未来需要 streams 或 dedicated GPU scheduler。

后续第 5 章会分别从 single-GPU contention 和 multi-GPU weak-scaling 两个角度评价这个设计。这些实验也解释了为什么实现中需要把 UVec handle manager 从 global lock 细化为 handle-level locking。

\section{小结}
本章给出了 FTCL 的系统设计：语言层负责表达，命令层负责连接，UVec 层负责跨设备数据一致性，CPU/CUDA 后端负责具体计算。这一架构的关键不在于某一个单独模块，而在于模块边界足够清楚，从而能够支持后续测试、基准与应用场景扩展。

FTCL 将控制、数据驻留与执行后端分离；UVec 是连接脚本层几何命令与底层 CPU/CUDA 内存管理的桥梁。
