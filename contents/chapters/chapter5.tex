\chapter{Evaluation}

\section{Evaluation Goals}
The evaluation answers three questions. First, does the language runtime preserve the intended semantics? Second, do CPU and CUDA geometry backends produce equivalent results? Third, when does CUDA provide an end-to-end speedup from the perspective of an FTCL script?

The project uses generated CSV files and figures under the \texttt{docs} directory. The measurements include semantic pass rate, parser backend timing, thread-channel latency, frame-time distribution, CPU/CUDA geometry speedup, throughput, numerical error, break-even point, ablation data, and concurrent geometry performance.

\section{Experimental Methodology}
All performance results in this thesis are treated as end-to-end system measurements unless explicitly stated otherwise. A geometry command measurement includes FTCL command dispatch, argument parsing, UVec handle lookup, device synchronization, output UVec allocation, backend execution, and synchronization after CUDA kernel launch. It does not represent pure CUDA kernel time. This choice is intentional because the thesis evaluates the experience of a script-level user.

The benchmark pipeline follows these principles.

\begin{enumerate}
  \item \textbf{Release builds are used.} Debug builds are excluded from performance discussion because interpreter dispatch and STL containers are highly sensitive to optimization level.
  \item \textbf{Warmup is separated from measurement.} Parser backend timing and geometry timing scripts perform warmup runs before recording samples when supported by the executable.
  \item \textbf{Median or percentile values are preferred.} Latency distributions are summarized using P50, P95, and P99. Geometry timing uses representative median command latency when multiple samples are available.
  \item \textbf{Readback is treated as a separate cost.} Some experiments keep results inside UVec handles, while ablation experiments explicitly measure the cost of converting large UVec outputs back into script lists.
  \item \textbf{CPU and CUDA results are compared before speed is interpreted.} CUDA speedups are meaningful only if CPU/GPU equivalence tests pass under the selected numerical tolerance.
\end{enumerate}

The main derived metrics are defined as follows:
\[
  \mathrm{speedup} = \frac{T_{\mathrm{CPU}}}{T_{\mathrm{CUDA}}},
  \quad
  \mathrm{throughput} = \frac{\mathrm{work\ items}}{T},
  \quad
  \mathrm{work\ items} = N \times Q.
\]
For distance matrix, nearest point, and range-count workloads, \(N\) denotes the number of data points and \(Q\) denotes the number of query points or query regions.

\subsection{CPU Baseline Definition}
The CPU baseline in this thesis is the FTCL CPU geometry backend, not a hand-tuned parallel CPU library. This distinction matters. The comparison is designed to answer the question a script user would ask: if the same FTCL command is executed with a CPU device and then with a CUDA device, how much end-to-end improvement is observed?

The CPU and CUDA rows therefore share the same script-level command path as much as possible. Inputs are prebuilt as UVec handles before timing in the main performance-scale benchmark. The timed section includes command dispatch, handle lookup, output UVec allocation, backend execution, and required synchronization. For the CPU row, the backend uses C++ scalar loops over CPU-resident UVec data. For the CUDA row, the backend uses CUDA device buffers and kernels, and the current CUDA helper calls \texttt{cudaDeviceSynchronize} after kernel launch so the command returns only after the backend work is complete.

This baseline is fair for evaluating FTCL as a heterogeneous scripting system, but it should not be interpreted as a comparison against an optimized all-core CPU geometry library. The server has 128 logical CPU threads, while the current CPU geometry backend is intentionally simple. Therefore, the reported speedup measures the benefit of moving the FTCL backend from its scalar CPU implementation to CUDA under the same command interface. A future all-core CPU backend would be a useful additional baseline.

\section{Multi-GPU Scaling}
The server contains eight A800 GPUs, so the evaluation also measures whether FTCL can expose more than one CUDA device to script-level geometry workloads. The multi-GPU benchmark uses weak scaling: each GPU receives the same number of query points, while the total number of queries grows with the GPU count. Each worker owns an independent FTCL interpreter, creates UVec inputs on a different CUDA device, and launches the same geometry command on \texttt{cuda:0}, \texttt{cuda:1}, \ldots, \texttt{cuda:7}. The reported speedup is throughput speedup relative to one GPU.

The benchmark must be run with all devices visible, for example:

\begin{lstlisting}[language=bash]
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 \
FTCL_MULTI_GPU_MODE=paper \
FTCL_MULTI_GPU_SCALING=weak \
test/bench_geometry_multi_gpu
\end{lstlisting}

In the recorded run, \(N=32768\), each GPU receives \(Q=4096\) query objects, and each row reports the median of three rounds. Thus the total query count is \(4096\), \(8192\), \(16384\), and \(32768\) for 1, 2, 4, and 8 GPUs respectively. The timer measures the wall-clock interval from simultaneously releasing all worker threads to all workers receiving their output UVec handles. Length checking and output destruction are performed after the timed region, so the timing focuses on command dispatch, UVec handle lookup, output allocation, CUDA launch, backend synchronization, and result-handle creation.

This experiment also revealed an important runtime bottleneck. The original UVec command manager protected the whole handle table with one global mutex and executed geometry commands while holding that mutex. As a result, independent CUDA commands could be serialized at the script runtime layer. The implementation was changed so that the global mutex only protects handle-table lookup, while each UVec handle has its own entry mutex. This allows independent UVec handles on different GPUs to execute concurrently.

Direct conclusion: circle range count shows near-linear multi-GPU throughput scaling, while distance matrix exposes output-dominant bottlenecks.

The result shows that multi-GPU execution is useful but algorithm-dependent. Circle range counting scales almost linearly to eight GPUs because each query produces one compact result and has regular independent work. Nearest point scales well to four GPUs and then drops at eight GPUs, suggesting that runtime overhead, allocation, and synchronization begin to dominate. Distance matrix has the weakest multi-GPU scaling because every query produces a large output row; output allocation and global memory traffic dominate the total command time. This is a useful negative result: the system can use eight GPUs, but future work needs memory pools, persistent output buffers, and CUDA streams to make large-output kernels scale better.

\section{Break-even Analysis}
CUDA acceleration has fixed overhead. A small workload may be slower on CUDA because kernel launch, synchronization, allocation, and command dispatch dominate the useful computation. Figure \ref{fig:break-even} uses work items \(N \times Q\) as the horizontal axis and speedup as the vertical axis.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.82\textwidth]{geometry-break-even.png}
  \caption{CUDA break-even analysis by work items}
  \label{fig:break-even}
\end{figure}

Direct conclusion: CUDA becomes worthwhile only after the work-item count is large enough to amortize launch, allocation, synchronization, and UVec management costs.

The stored data estimates the break-even point at about 8192 work items for distance matrix, about 47848 for nearest point, and about 121209 for circle range count. These values are not universal constants. They depend on hardware, driver state, input size, output size, and whether the measurement includes readback.

\section{Ablation and Concurrent Geometry}
The ablation experiment separates inline literal parsing, prebuilt UVec handles, and readback overhead. It shows that prebuilt handles can greatly reduce command latency, especially for CUDA commands. It also shows that reading large outputs back to a script list can dominate total time. Therefore, a high-performance script should keep data in UVec form across multiple geometry commands and only read back final summaries.

\begin{table}[H]
\centering
\caption{Interpretation of the geometry ablation experiment}
\label{tab:ablation-interpretation}
\begin{tabularx}{\textwidth}{lX}
\toprule
Experiment mode & Interpretation \\
\midrule
Inline literal input & Measures the full cost of parsing point lists from script text, creating temporary data structures, dispatching the command, and executing the backend. This mode is convenient but can be dominated by script parsing for large inputs. \\
Prebuilt UVec without readback & Measures the cost of handle lookup, device synchronization, output allocation, and backend execution while keeping data resident in UVec form. This mode best represents a high-throughput script pipeline. \\
Prebuilt UVec with readback & Adds the cost of converting the output UVec into a script list. For large outputs such as distance matrices, this can dominate total time and hide the benefit of CUDA computation. \\
\bottomrule
\end{tabularx}
\end{table}

The ablation result leads to a practical design rule: FTCL scripts should use UVec handles as long-lived data objects and should avoid converting large intermediate results back into strings. This is similar to the principle of data residency in GPU programming. Acceleration is strongest when data is copied to the device once, processed by several commands, and read back only at the end.

The same interpretation also explains why CUDA is not always faster for small inputs. Even if the kernel itself is efficient, the total command path still pays fixed costs for launch, synchronization, output allocation, and possible readback. Therefore, the break-even point is a system-level property, not just an algorithmic property.

The concurrent geometry experiment is shown in Figures \ref{fig:concurrency-throughput} and \ref{fig:concurrency-latency}. CPU throughput improves with more workers until contention appears. CUDA throughput is flatter because multiple script workers compete for one GPU and synchronization point.
