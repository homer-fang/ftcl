\chapter{系统实现}

\section{Interpreter Core}
FTCL 的实现主要采用 header-based 结构，核心代码位于 \texttt{include} 目录。Interpreter 被构建为 CMake interface library，测试和 benchmark executables 位于 \texttt{test} 目录。CUDA 支持由 \texttt{FTCL\_ENABLE\_CUDA} CMake option 控制，因此同一套代码可以在 CPU-only 环境和 CUDA 环境下分别构建。

Value representation 遵循 Tcl-style 的思想：脚本层 value 首先是 string，但内部可以缓存结构化 data representation。例如，一个 value 可以由 integer、floating-point number、Boolean、list、dictionary 或 variable name 构造；当用户请求 string representation 时，再 lazy formatting。这样既保持了 string-oriented script interface，又减少了重复格式化带来的开销。

Interpreter core 的另一个设计目标是保持 command extensibility。语言核心并不直接理解所有高级功能，而是通过 command table 分发。\texttt{expr}、\texttt{thread}、\texttt{uvec} 和 \texttt{geom} 都以 command 的形式进入系统。这使得 FTCL 可以逐步扩展，而不需要频繁改变 parser grammar。

\section{Expression Parser}
Expression parser 使用 recursive-descent precedence hierarchy。顶层函数解析 conditional expressions，然后逐层下降到 logical OR、logical AND、bitwise operators、equality、relational operators、shifts、additive operators、multiplicative operators、unary operators 和 primary expressions。

例如，\texttt{a || b \&\& c} 由 logical OR layer 处理。左操作数先被解析为 logical AND expression；匹配到 OR operator 之后，右操作数再次按 logical AND expression 解析，因此 \texttt{b \&\& c} 会先结合，再参与 OR operation。这种写法虽然不是 Pratt parser，但优先级边界非常直观，适合当前表达式子系统。

Expression parser 还支持 short-circuit evaluation。如果 \texttt{||} 的左操作数已经为 true，右操作数仍然会被 parser 扫过以保持 syntax validation 和 parser position，但不会真正执行变量读取、command substitution 或可能产生 side effects 的求值动作。这一点对 Tcl-style expression 很重要，因为表达式里可能包含 \texttt{\$var} 和 \texttt{[script]}。

\begin{algorithm}[H]
\caption{Expression Evaluation and Conditional Operator}
\label{alg:expr-eval}
\KwInput{interpreter $interp$, expression string $input$}
\KwOutput{expression value}
\Proc{\textsc{EvalExpr}($interp$, $input$)}{
  $parser \leftarrow \textsc{ExprParser}(interp, input)$\;
  $value \leftarrow parser.parseConditional()$\;
  $parser.skipWhitespace()$\;
  \If{not $parser.atEnd()$}{
    raise ``unexpected token in expression''\;
  }
  \KwReturn{$value$}\;
}
\Proc{\textsc{ParseConditional}($parser$)}{
  $condition \leftarrow \textsc{ParseLogicalOr}(parser)$\;
  \If{not $parser.match(\texttt{?})$}{
    \KwReturn{$condition$}\;
  }
  $takeTrue \leftarrow condition.isTrue()$\;
  $parser.setEvaluationEnabled(takeTrue)$\;
  $trueValue \leftarrow \textsc{ParseLogicalOr}(parser)$\;
  $parser.expect(\texttt{:})$\;
  $parser.setEvaluationEnabled(\neg takeTrue)$\;
  $falseValue \leftarrow \textsc{ParseConditional}(parser)$\;
  $parser.restoreEvaluationMode()$\;
  \uIf{$takeTrue$}{
    \KwReturn{$trueValue$}\;
  }
  \Else{
    \KwReturn{$falseValue$}\;
  }
}
\end{algorithm}

\begin{algorithm}[H]
\caption{Logical OR Short-circuit Evaluation}
\label{alg:expr-or}
\KwInput{expression parser $parser$}
\KwOutput{logical OR result}
\Proc{\textsc{ParseLogicalOr}($parser$)}{
  $lhs \leftarrow \textsc{ParseLogicalAnd}(parser)$\;
  \While{$parser.match(\texttt{||})$}{
    \uIf{$lhs.isTrue()$}{
      $parser.setEvaluationEnabled(false)$\;
      \textsc{ParseLogicalAnd}($parser$)\tcp*[r]{parse only; no side effects}
      $parser.restoreEvaluationMode()$\;
      $lhs \leftarrow 1$\;
    }
    \Else{
      $rhs \leftarrow \textsc{ParseLogicalAnd}(parser)$\;
      $lhs \leftarrow bool(lhs) \lor bool(rhs)$\;
    }
  }
  \KwReturn{$lhs$}\;
}
\end{algorithm}

\section{UVec Implementation}
UVec 要求 element type 满足 trivially copyable。这个约束不是形式主义，而是跨 CPU/CUDA byte copy 的基础：如果一个类型需要复杂构造、析构或内部指针修正，那么直接 memcpy 到 device memory 并不安全。围绕 UVec 的主要辅助类型包括 \texttt{Device}、\texttt{RawUPtr<T>}、\texttt{RawUMutPtr<T>}、\texttt{UniversalCopy} 和 \texttt{Zeroable}。

Script-level \texttt{uvec} command 负责管理 UVec handles。它可以从 list 创建 vector，创建 filled 或 zeroed vector，读取或设置元素，返回 vector length，同步到指定 device，并将 vector 转回 script list。Command manager 将 handle-to-UVec mapping 放在 mutex 保护下，使脚本可以安全地在不同 command 之间传递 handle。

\begin{algorithm}[H]
\caption{UVec Read Synchronization}
\label{alg:uvec-read}
\KwInput{UVec object $uvec$, target device $device$}
\KwOutput{read-only unified pointer}
\Proc{\textsc{AsUPtr}($uvec$, $device$)}{
  \uIf{$device = \mathrm{CPU}$}{
    \If{CPU buffer is not valid}{
      $source \leftarrow$ any valid CUDA buffer\;
      copy $source$ CUDA buffer to CPU buffer\;
      mark CPU buffer valid\;
    }
    \KwReturn{\textsc{RawUPtr}(CPU pointer, length, CPU)}\;
  }
  \Else{
    ensure CUDA buffer for $device$ exists\;
    \If{target CUDA buffer is not valid}{
      \uIf{CPU buffer is valid}{
        copy CPU buffer to target CUDA buffer\;
      }
      \Else{
        $source \leftarrow$ another valid CUDA buffer\;
        copy $source$ CUDA buffer to target CUDA buffer\;
      }
      mark target CUDA buffer valid\;
    }
    \KwReturn{\textsc{RawUPtr}(CUDA pointer, length, $device$)}\;
  }
}
\end{algorithm}

\begin{algorithm}[H]
\caption{UVec Mutable Pointer Access}
\label{alg:uvec-write}
\KwInput{UVec object $uvec$, target device $device$}
\KwOutput{mutable unified pointer}
\Proc{\textsc{AsMutUPtr}($uvec$, $device$)}{
  ensure storage exists on $device$\;
  \If{target device is not valid}{
    synchronize latest data to target device\;
  }
  \ForEach{$other \in$ devices and $other \ne device$}{
    mark $other$ invalid\;
  }
  mark $device$ valid and newest\;
  \KwReturn{\textsc{RawUMutPtr}(target pointer, length, $device$)}\;
}
\end{algorithm}

\section{CPU Geometry Algorithms}
CPU geometry library 实现在 \texttt{include/geometry.hpp} 中，基础类型包括 Point、Segment 和 BoundingBox。库中实现了 distance、squared distance、dot product、cross product、orientation、point-on-segment checks、segment intersection、line intersection、point-line distance、point-segment distance、polygon area、polygon perimeter、point-in-polygon classification、convex hull、bounding box 和 closest-pair distance。

Batch algorithms 使用 flattened arrays。点集按 \(x_0,y_0,x_1,y_1,\ldots\) 存储；线段集按每条线段 \(x_1,y_1,x_2,y_2\) 存储；AABB 集合按 \(min_x,min_y,max_x,max_y\) 存储。这个格式对 script、UVec 和 CUDA kernel 都友好，因为它避免了复杂对象布局，也便于跨设备拷贝。

\section{CUDA Geometry Backend}
CUDA backend 实现在 \texttt{src/geometry\_cuda.cu} 中，对外声明位于 \texttt{include/geometry\_cuda.hpp}。它支持 distance matrix、nearest point、circle range count、point transformation、batch orientation、AABB collision、polygon batch area 和 distance to polyline 等 data-parallel algorithms。

以 \(N\) 个 source points 和 \(Q\) 个 query points 的 distance matrix 为例，输出规模为 \(NQ\)。CUDA mapping 非常直接：每个 thread 负责一个 output entry，读取一个 source point 和一个 query point，计算 Euclidean distance，并写回结果。这类映射适合 GPU，因为每个 output element 彼此独立，控制分支少，且 work-item 数量可以快速增长。

\section{Script Interface}
下面的示例展示了脚本如何创建两个 point sets，运行 CUDA nearest-point query，并读取结果。

\begin{lstlisting}[language=bash,caption={FTCL geometry scripting example}]
set dataset [geom uvec_points {{0 0} {1 2} {3 4} {5 8}} cuda:0]
set query   [geom uvec_points {{2 2} {4 6}} cuda:0]
set result  [geom nearest_point $dataset $query cuda:0]
puts [uvec to_list $result]
\end{lstlisting}

用户不需要手动分配 device memory。Script 只描述任务；UVec 管理 synchronization；\texttt{geom} command 选择 CPU 或 CUDA backend。这正是 FTCL 作为异构脚本系统的价值：把底层细节收进系统，把表达能力留给用户。

\begin{algorithm}[H]
\caption{Geometry Command Dispatch for Nearest-point Query}
\label{alg:geom-dispatch}
\KwInput{interpreter $interp$, command arguments $argv$}
\KwOutput{UVec handle containing nearest-point results}
\Proc{\textsc{GeomNearestPoint}($interp$, $argv$)}{
  $datasetId \leftarrow \textsc{ParseHandle}(argv[2])$\;
  $queryId \leftarrow \textsc{ParseHandle}(argv[3])$\;
  $device \leftarrow \textsc{ParseOptionalDevice}(argv[4], \mathrm{CPU})$\;
  $dataset \leftarrow uvecManager.lookup(datasetId)$\;
  $queries \leftarrow uvecManager.lookup(queryId)$\;
  \uIf{$device$ is CUDA}{
    $datasetPtr \leftarrow dataset.asUPtr(device)$\;
    $queryPtr \leftarrow queries.asUPtr(device)$\;
    $output \leftarrow \textsc{UVec.Uninitialized}(queryCount \times 2, device)$\;
    $outputPtr \leftarrow output.asMutUPtr(device)$\;
    launch \textsc{NearestPointCuda}($outputPtr$, $datasetPtr$, $queryPtr$)\;
    \KwReturn{$uvecManager.create(output)$}\;
  }
  \Else{
    $datasetCpu \leftarrow dataset.cpuVector()$\;
    $queriesCpu \leftarrow queries.cpuVector()$\;
    $values \leftarrow \textsc{NearestPointCpu}(datasetCpu, queriesCpu)$\;
    $output \leftarrow \textsc{UVec.FromCpu}(values)$\;
    \KwReturn{$uvecManager.create(output)$}\;
  }
}
\end{algorithm}

\section{小结}
本章说明了 FTCL 从语言核心到 CUDA backend 的实现方式。Interpreter core 提供可扩展的 command dispatch；expression parser 处理带 short-circuit 的运行时表达式；UVec 把跨设备内存管理压缩为 read/write pointer 接口；geometry library 则把算法暴露为脚本命令。

The implementation is intentionally practical: it favors clear interfaces over hidden magic. FTCL becomes useful because each layer can be tested independently and composed through script-visible commands.
